# Minecraft 26.2 机制速查（Quirky 开发笔记）

> 26.2 重构了大量机制，**旧版本知识不可靠**。以下每一条都经 `$HOME/.cache/mcsrc` 源码实锤，附源码位置。开发新功能前先查本表，再查 mcsrc 确认。

## 1. 服务端粒子

- **症状**：服务端调用 `level.addParticle(...)` 粒子不显示。
- **根因**：`Level.addParticle` 是**空实现**（`Level.java:499-500`），仅 `ClientLevel` 覆盖（客户端本地生成）。
- **正确做法**：服务端必须 `serverLevel.sendParticles(ParticleOptions, x, y, z, count, xDist, yDist, zDist, speed)`（`ServerLevel.java:1304`，广播 32 格内玩家）。

## 2. 音效音量与衰减

- **响度**：`SoundEngine.calculateVolume` 把音量 **clamp 到 1.0**（`SoundEngine.java:469-470`）——音量 >1 不影响响度。
- **衰减距离**：`衰减距离 = max(客户端实例音量, 1.0) × Sound.attenuationDistance`（`SoundEngine.java:378`）；Sound.attenuationDistance 默认 16（`Sound.java:44`），**sounds.json 可自定义 `"attenuation_distance"`（如 64）**。
- **客户端实例音量 = 包音量 × 音效定义音量**（`SoundManager.java:308` MultipliedFloats）——**原版音效定义音量折减会拉低响度与衰减距离**（如原版紫水晶叮声定义音量 ~0.26 → 包音量再大衰减也只有 ~20 格）。
- **广播范围**：服务端只发给 `SoundEvent.getRange(volume)` 内玩家 = `16 × volume`（>1 时，`SoundEvent.java:49-51`）——音量 >1 同时拉长广播与衰减距离。
- **自定义音效（sounds.json）**：
  - key 不带 namespace（`SoundManager` 遍历 namespace 时拼接）；**name 用 `Identifier.parse` → 不带 namespace 默认 `minecraft:` 前缀**——必须写完整（`"name": "quirky:totem/chime"` 或 `"minecraft:block/amethyst_block/chime"`）。
  - 引用原版文件可**覆盖 volume**（引用文件 ≠ 引用原版 SoundEvent，绕开原版定义音量折减）——原版紫水晶 chime 文件名实锤：`minecraft:block/amethyst_block/chime`（26.2 参考资源包 VerdantVice 证实）。
  - 字段名：`"attenuation_distance"`（`SoundEventRegistrationSerializer.java:60`）、`"volume"`、`"pitch"`、`"weight"`、`"replace"`。
- **SoundSource**：`Entity.getSoundSource()` 默认 `NEUTRAL`（`Entity.java:3616`）——受"友好生物"滑块控制。
- **随机 vs 固定间隔**：`random.nextInt(N)==0` 是指数分布间隔（平均 N/20 秒，可能极短导致音效重叠、也可能极长）——需要稳定节奏用计数器（`++ticks >= INTERVAL`）。
- 环境音折腾结论：**自定义音效链路复杂（注册/定义/namespace/音量系数），小需求优先用原版 SoundEvent 直接播放**；本项目图腾环境周期音已删除（用户决定）。

## 3. 实体渲染（EntityRenderState 模式）

- 26.2 渲染管线：`EntityRenderer<T extends Entity, S extends EntityRenderState>` 实现 `createRenderState()` / `extractRenderState(T, S, float)` / `submit(S, PoseStack, SubmitNodeCollector, CameraRenderState)`（模板：`ItemEntityRenderer.java`）。
- **没有 `getTextureLocation` 抽象方法**（旧版有，已移除）。
- 物品渲染：`ItemEntityRenderState.extractItemGroupRenderState(Entity, ItemStack, ItemModelResolver)`（`ItemClusterRenderState.java:15`）→ `ItemStackRenderState.submit(...)`。

## 4. 实体数据序列化（ValueOutput/ValueInput）

- **不是 CompoundTag + HolderLookup**！实体 NBT：`addAdditionalSaveData(ValueOutput)` / `readAdditionalSaveData(ValueInput)`（`Entity.java:2210`）。
- 物品列表：`output.store("Items", ItemStackWithSlot.CODEC.listOf(), list)`；UUID 用 `putLong` 两半。
- `ItemStackWithSlot` 在 **`net.minecraft.world` 包**（record：`slot()` / `stack()`），自带 CODEC。
- 测试构造：`TagValueOutput.createWithContext(ProblemReporter.DISCARDING, provider)` / `TagValueInput.create(..., tag)`（`ProblemReporter.nope()` **不存在**，用 `DISCARDING`）。

## 5. 伤害与攻击

- `Entity.hurt` 是 @Deprecated final，转发 **`hurtServer(ServerLevel, DamageSource, float)`**（`Entity.java:1920-1931`）——override `hurtServer` 即可感知攻击且不受伤。
- 玩家攻击：`Player.attack(Entity)` → `hurtOrSimulate` → `hurtServer`，**无 invulnerable 短路**（`Player.java:945` 起）。
- 近战判定：`source.is(DamageTypes.PLAYER_ATTACK)`；`source.getEntity()` 是 causing entity（含间接）。

## 6. 客户端实体拾取（关键！）

- **症状**：非 LivingEntity 实体（继承 `Entity` 基类）玩家怎么点都没反应——攻击请求根本没发出。
- **根因**：客户端射线拾取用 `EntitySelector.CAN_BE_PICKED = Entity::isPickable`（`EntitySelector.java:17`），而 `Entity.isPickable()` 默认 **false**（`Entity.java:2012`）——LivingEntity 才默认 true。
- **正确做法**：可交互的非 LivingEntity 实体必须 `@Override public boolean isPickable() { return true; }`。

## 7. 实体注册

- `EntityType.Builder.of(factory, MobCategory.MISC).sized(...).build(ResourceKey)` **只构造不注册**——需 `Registry.register(BuiltInRegistries.ENTITY_TYPE, key, type)`（照 ModBlocks/ModItems 模式）。
- `EntityType` 构造会 `createIntrusiveHolder`（`EntityType.java:56`）——**必须在注册表冻结前加载**：测试里 `TestBootstrap.boot()` 要在注册窗口内（`setBootstrapped(true)` 与 `Bootstrap.bootStrap()` 之间）调用 `ModEntities.register()`，否则惰性类加载晚于冻结会崩溃。

## 8. 物品模型注册（紫黑 bug 根因）

- 26.2 物品模型定义走 **`assets/<ns>/items/<id>.json` 新格式**：`{"model": {"type": "minecraft:model", "model": "quirky:item/<id>"}}`。
- 只写旧格式 `models/item/<id>.json` **不生效** → 物品/实体渲染紫黑棋盘格。
- 新物品三件套：`items/<id>.json` + `models/item/<id>.json` + `textures/item/<id>.png`。

## 9. 重生点与维度

- 玩家重生点：`ServerPlayer.getRespawnConfig()`（nullable）→ `respawnData().globalPos()`（`ServerPlayer.java:1958`）；`getRespawnPosition()` **不存在**。
- 世界出生点：`level.getLevelData().getRespawnData().globalPos().pos()`。
- 跨维度判断：比较 `level.dimension()`（`ResourceKey<Level>`）与重生点 `globalPos().dimension()`。

## 10. 其他 26.2 API 差异

| 旧知识 | 26.2 实际 |
|---|---|
| `ResourceKey.location()` | **`ResourceKey.identifier()`**（`ResourceKey.java:64`） |
| `GameRules` 在 `world.level` | **`net.minecraft.world.level.gamerules`** 包；`level.getGameRules().get(GameRules.KEEP_INVENTORY)` 返回 `Boolean` |
| `Inventory.getFreeSlot()` 查全背包 | **只查物品栏 36 格**（`Inventory.java:101`），满则 -1 |
| `Inventory.clearContent()` | `items.clear() + equipment.clear()`，43 槽全清 |
| 玩家攻击入口 `Entity.attack(Entity)` | 已移除；玩家攻击走 `Player.attack` → `hurtOrSimulate` |
| `ItemStack.setHoverName` | **不存在**；用 `set(DataComponents.CUSTOM_NAME, ...)` |
| Mixin target `dropAllDeathLoot(Level, ...)` | 描述符是 **`(ServerLevel, DamageSource)V`**（`ServerPlayer.die` 内联调用，javap 实锤） |
| `EnchantmentEffectComponents` 包 | `net.minecraft.world.item.enchantment`（不是 core.component） |
| 附魔注册表 | datapack registry；测试环境用 `Holder.direct` 构造（无注册表可取 Holder） |

## 11. 测试环境注意

- `TestBootstrap.boot()` + `bindItem(Item)`：绑定 vanilla initializer（equippable 等）。
- mock 实体安全：`Entity` 构造/`discard` 不依赖 level（`levelCallback` 默认 `EntityInLevelCallback.NULL`，`Entity.java:280`）。
- mock `DamageSource` / `ServerLevel` / `Level` 均可（Mockito inline 支持 final）。

## 12. Cloth Config API 适配结论

- **版本**：maven `me.shedaniel.cloth:cloth-config-fabric:26.2.155`（对应 MC 26.2）；ModMenu `com.terraformersmc:modmenu:20.0.0-beta.2`
- **官方红线**："DO NOT use Auto Config / Cloth Config for server mods"——AutoConfig 无 `@ServerConfig` 注解（v26.2 源码实锤），dedicated server 行为参数由服主改配置文件决定，客户端 GUI 不推送服务端
- **双端注册**：AutoConfig 在 `ModInitializer` 注册，双端进程各自读写自己的 `config/quirky.json5`；单机/局域网共享目录，GUI 修改直接生效
- **load() 替换实例**：`ConfigHolder.load()` 会反序列化新实例替换内部引用——静态缓存持有者必须在 load 后重新注入，否则热重载失效
- **测试隔离**：配置读取走静态 holder，测试注入默认实例，不注册 AutoConfig（不碰文件系统）

## 13. 方块模型替换与粒子 sprite（灵魂光源验证结论）

- **BlockModelShaper 已移除**：26.2 方块模型按 BlockState 从 `ModelManager.getBlockStateModelSet().get(BlockState)` 派发，模型解析无位置信息
- **模型替换注入点**：唯一同时持有渲染区域（`BlockAndTintGetter`）与 `BlockPos` 的网格入口是 `SectionCompiler.compile` 调用 `ModelBlockRenderer.tesselateBlock(BlockQuadOutput, float×3, BlockAndTintGetter, BlockPos, BlockState, BlockStateModel, long)`——在此 @Redirect 可按 y-1 邻居动态换模型（无状态存储，区块重编译时重评估）
- **BakedQuad 换 sprite 必须重打包 packedUV**：packedUV 存的是旧 sprite 的图集绝对坐标（float 对，高 32 位 u 低 32 位 v，`UVPair.pack/unpackU/unpackV`）；直接换 materialInfo 的 sprite 会采样错位。还原模型 UV：`modelU = (u - sprite.getU0()) / (sprite.getU1() - sprite.getU0()) * 16`，再经新 sprite `getU/getV` 重打包
- **26.2 蜡烛模型结构**（template_candle 系列，candle_one_candle/candle_two_candles/...）：火焰是蜡烛顶部的两个交叉小面（uv `[0,5,1,6]`，采样 lit 纹理 (0,5) 像素）；烛身面采样纹理其余区域（侧面 `[0,8,2,14]`、顶面 `[0,6,2,8]`、底面 `[0,14,2,16]`）——只替换 UV 落在 v∈[5,8) 的 quad 即得"火焰变灵魂青色、烛身保色"
- **粒子图集 sprite id**：particles atlas（`assets/minecraft/atlases/particles.json`，directory source prefix=""）的 id **无 `particle/` 前缀**，如 `soul_fire_flame`；获取：`Minecraft.getInstance().getAtlasManager().get(new SpriteId(TextureAtlas.LOCATION_PARTICLES, Identifier.withDefaultNamespace("soul_fire_flame")))`
- **FlameParticle**：构造为 private `(ClientLevel, double×6, TextureAtlasSprite)`（Provider 内创建）；`setSprite(TextureAtlasSprite)` 在父类 SingleQuadParticle 为 protected——mixin `@Shadow protected abstract` + `@Inject(<init>, TAIL)` 可换粒子 sprite；火把/蜡烛 animateTick 的粒子 y 均在方块上半部，`BlockPos.containing(x, y, z)` 必落在光源方块自身、其下方 y-1 为支撑方块
- **粒子替换必须限定光源方块**：`ParticleTypes.FLAME` 不只火把/蜡烛使用，熔炉（y+dy，dy<0.375）、刷怪笼、岩浆怪等也生成 FlameParticle——只查“粒子下方为灵魂方块”会把灵魂沙上的熔炉火焰也染青。正确做法：先判定粒子所在方块为光源方块（`isLightSource`：TORCH/WALL_TORCH/LANTERN/CandleBlock，排除 SOUL_TORCH/SOUL_LANTERN 等已灵魂化的变体），再判定其下方为灵魂方块
- **区块网格注入点要过滤方块类型**：`SectionCompiler.compile` 的 @Redirect 对区块内每个方块都执行，必须先做低成本的光源方块类型判定（`SoulLightingHelper.isLightSource`），命中才查询 `pos.below()` 邻居，避免每方块一次 `getBlockState` 的额外开销
- **灵魂方块判定**：`Blocks.SOUL_SAND`/`SOUL_SOIL`；蜡烛判定 `instanceof CandleBlock`（含 16 色，CandleCakeBlock 不是 CandleBlock）；lit 用 `AbstractCandleBlock.LIT`
- **孤儿模型依赖 directory 图集（review S2）**：`assets/quirky/models/block/soul_candle[_lit].json` 无任何 blockstate/items 引用（灵魂蜡烛火焰靠 `SectionCompiler.compile` 动态换 sprite），能进图集是因为 26.2 方块图集 `atlases/blocks.json` 是 `"type":"minecraft:directory" source:"block"`（直接扫目录）。**若未来图集改回显式 materials 源，灵魂蜡烛火焰会静默变紫黑**——版本升级时检查该图集定义。

## 14. Fabric HUD 元素注册（使用量挂件崩溃）

- **`HudElementRegistry.addLast(id, element)` 对任意 vanilla id 首次调用即抛 `IllegalArgumentException: Layer with identifier minecraft:hotbar already exists`**
- **根因**：`HudElementRegistryImpl` 静态块把 23 个原版元素（含 `minecraft:hotbar`）预注册为 `ROOT_ELEMENTS` RootLayer，每个自带同 id 的 vanilla layer → `addLast` 的 `validateUnique` 必命中（除非用全新 namespace id）。不要在 vanilla id 上用 `addLast`/`addFirst`。
- **正确 API**：`HudElementRegistry.attachElementAfter(rootId, elementId, element)` / `attachElementBefore`——在指定原版元素（如 `VanillaHudElements.HOTBAR`）后/前插入**新的** mod 元素 id，此时 `validateUnique` 校验的是新 elementId（唯一）而非 rootId。`HudElementRegistryImpl` 包路径 `net.fabricmc.fabric.impl.client.rendering.hud`（javap 实锤）。
- 此坑首次真实运行才暴露（编译+单测均不覆盖）——客户端初始化崩溃 `Initializing game` 定位到入口点再查 HUD 注册链。
- **HudElementRegistry 26.2 用法（实测崩溃教训）**：fabric-rendering-v1 25.3.1 静态初始化即把 23 个原版元素（MISC_OVERLAYS/CROSSHAIR/HOTBAR/...）注册为 RootLayer（各带同 id vanilla layer）；`addLast/addFirst(原版元素id, ...)` 的 validateUnique 第一次就会抛 `Layer with identifier minecraft:hotbar already exists`。正确用法：`attachElementAfter(VanillaHudElements.HOTBAR, modId("usage_ticker"), HudElement)` / `attachElementBefore`——校验的是新元素 id。
